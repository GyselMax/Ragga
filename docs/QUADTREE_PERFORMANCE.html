Why about 2× slower, and why it isn't your code

Your builder is the same code as Q16's NodeQuadtree, and it's 2× slower too, as is the plain 9-starter run. So the gap comes from the setup: a different PC (your last commit moved PCs) and slightly different search points. The ratios, which don't depend on the machine, match or beat the notes. Seed 67's plain time is lower than in Q8 because Q8 timed a single cold run, before the JIT had warmed up.

With the Q21 wiring, every candidate in a street step runs its own 240 search for crossings. Once that search happens once per step, the biggest cost is JGraphT itself: each crossing test asks the graph for a street's two ends, which is a HashMap lookup each.

36 starters, 11,106 nodes. Plain loops take 112,977 ms, 106 times the top bar. Change 4 was measured in a separate run (507 → 439 ms, −14%), and its bar is scaled from that.

  1. Do the 240 search once per street step −43%

    growStreet / isCrossingFree

    Every candidate asks the same question around current, and no street is added until the step ends. So search once per step and reuse the nearby streets for every candidate. Take each street only from its source end: both ends always lie within 240, so this halves the crossing tests.

  2. Check triangles without building sets −5%

    isTriangleFree

    Collections.disjoint(neighborSetOf(a), neighborSetOf(b)) builds two sets for every candidate. Looping over a's streets and asking graph.containsEdge(otherEnd, b) gives the same answer without building anything.

  3. Keep the step's streets as end-node pairs −17%

    the list from change 1

    Store each street's two Nodes when you collect them. Every crossing test after that is plain arithmetic, with no getEdgeSource/getEdgeTarget lookups.

  4. Use SimpleGraph instead of SimpleWeightedGraph −14% one word

    GraphGenerator.java:53

    No street ever gets a weight. In a weighted graph, JGraphT can't read a DefaultEdge's ends from the edge itself, so every getEdgeSource and getEdgeTarget becomes a HashMap lookup. SimpleGraph reads them straight from the edge. The city is the same, and even the plain loops get 31–38% faster. If you want weights later, use DefaultWeightedEdge instead.

Not worth it yet

Arrays instead of lists in Leaf/Branch (Q16: 10–15% per search), or reusing one list instead of findWithin (1–11% per search). Searches are about a quarter of the run, so each would save only a few percent overall.
