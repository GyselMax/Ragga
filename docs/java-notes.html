Q23 · One distance test

Why does Leaf.collectWithin do its own math for each node instead of using touches?

Short answer

Because they answer two different questions. touches asks whether the circle reaches a square, which is an area, so it first finds the square's point closest to the centre with clamp. The loop asks whether one node, a single point, is inside the circle. There's nothing to clamp there, because the node already is the point. You're right, though, that both end with the same sum: dx² + dy² ≤ radius². That part can be one shared helper, within(px, py, x, y, radius), and touches becomes "clamp, then within". I tested that version: same results, same city.

The shared helper

Tested like Q21: compiles with your real Node.java, matches a loop over all nodes, and seed 67 still gives the identical 326 nodes and 549 streets. Q21 still does the sums inline. Both versions behave exactly the same, so pick the one that reads better to you. QuadTreeBuilder is in the same package and can call QuadSquare.within too.

Why it says QuadSquare.within, not just within

Static methods in an interface aren't inherited. Inside QuadSquare itself, like in touches, a plain within(…) works. But Leaf only implements the interface, so a plain call there doesn't compile: error: cannot find symbol … method within(double,double,double,double,double). That's the actual error from the test, so it has to be written as QuadSquare.within(…). A default method like touches is inherited, which is why Leaf can call touches(…) without the prefix.

Why the leaf still calls touches first

Its parent Branch already touched the circle, but that only means at least one of the four children might. Each child checks its own square. For a leaf that misses, one touches test skips all of its nodes, up to 8, without measuring any of them.

Q22 · findWithin

Why does findWithin return void and fill a list? And are x and y relative to the square, or to the whole map?

Short answer

You're right that callers should get a list back, and the final code in Q21 now does that. The list parameter is there for the recursion. Every square adds to one shared list, instead of each square making its own list and its parent copying them all together. Making every level return its own list measured 2.4× slower. So the final version has both: findWithin(x, y, radius) returns a new list for you to use, and collectWithin(x, y, radius, result) does the recursive work underneath. That costs 3 to 10% over reusing one list, which doesn't matter at this size. And x and y are always map coordinates: the centre of the search circle, the same kind of number as node.getX() and getY(). Every square gets the same x and y, and compares them with its own minX, minY and size, which are map coordinates too.

Why the recursive part fills one list

A search visits about 20 squares on average, more for a big radius. On the left, each of those makes a list, and every node found gets copied again on each level it passes on the way back up. On the right there's one list per search, and each node is added to it once.

The names say which is which

A method called find… gives you something back. One called collect… puts its findings into the list you pass it. Keeping both names makes it clear at the call site whether a new list is made.

When to use collectWithin yourself

Only in a loop that runs very often and can reuse one list: nearby.clear(); tree.collectWithin(x, y, r, nearby);. That saves the 3 to 10%. Everywhere else, findWithin reads better.

Q20 · Memory

In a bigger city the quadtree holds a lot of leaves and branches. Won't that use a lot of memory if it isn't stored in a database?

Short answer

No. The tree is small for two reasons. It doesn't copy your nodes, it only points at them, and there are far fewer squares than nodes: one square for every 2 to 3 nodes. Measured, the frozen tree takes 0.28 MB for an 11,000-node city and 3.4 MB for 100,000 nodes. That's less than the nodes themselves, and about a fifteenth of the JGraphT street graph you already keep in memory. Even a million nodes needs 40 MB, while your JVM may use up to 8 GB by default. A database wouldn't save memory either: to search the tree you'd have to load it back, or ask MySQL on every search, which is roughly a thousand times slower.

Why it's small

It points, it doesn't copy

A leaf's list holds references to your existing Node objects, about 4 bytes each. The x, y and everything else stay in the one Node object you already have.

Few squares, each small

A leaf holds up to 8 nodes, so there's one square for every 2 to 3 nodes. Each square is around 90 bytes: three doubles plus a small list.

The builder goes away

Once build() has made the QuadTree, nothing points at the builder any more, and Java's garbage collector frees it. From then on, only the frozen tree is left.

The graph is the big one

JGraphT keeps, for every node, a set of its edges inside hash maps, plus an object per edge. That's where the 550 bytes per node go. If memory ever gets tight, the graph is where to look first, not the tree.

So the split from Q12 still holds: save the nodes and streets in MySQL, because they're the real data, and keep the tree in memory, rebuilding it after loading. MySQL can index positions too, with a SPATIAL INDEX, which is an R-tree, a close cousin of the quadtree. That becomes useful later, if the API needs "which buildings are in this rectangle" straight from the database. It's not something the generator needs.

When memory would start to matter

With many big cities loaded at the same time, or tens of millions of nodes. Even then, look at the street graph first: at 100,000 nodes it takes 52 MB against the tree's 3.4 MB.

Names to avoid

Frozen for the interface

Java interfaces are nouns, like List, or abilities, like Comparable. Frozen is an adjective with no noun: Frozen root doesn't say what root is. And the interface is one square, not the tree.

QuadNode for a square

Books on quadtrees call the squares "nodes", but in your code Node already means an intersection in the city. QuadSquare keeps "node" meaning one thing.

QuadTree or Quadtree: both spellings are common. Pick one and use it everywhere.

Q18 · Why freeze

Why would you need to freeze the tree into records?

Short answer

You don't need to. Freezing only exists because you wanted separate Leaf and Branch types (Q15). The tree can't be built with them, because splitting a leaf would mean swapping objects (Q14), so you build with NodeQuadtree and convert once at the end. If one class is fine for you, skip freezing and use NodeQuadtree everywhere: same results, and slightly faster (Q16). The records aren't the point either. A record is just the shortest way to write a class whose fields can't change, and final classes do the same job.

What freezing gets you

A tree that can't change

After node generation, nothing can insert into it by accident. Every later step, like streets, districts or distance checks, sees exactly the same tree, and you can hand it to a visualizer or another thread without copying it.

The types you asked for

Leaf and Branch, with no nulls, and polymorphism behind QuadSquare: root.findWithin(…) works without checking which kind it is.

Work done once

The list of leaves is collected while freezing, so later steps get it for free instead of walking the tree each time.

You already freeze something

CityConfig's compact constructor does starters = List.copyOf(starters);, with your own comment: "immutable copy, so the config can't change after it's built". Freezing the tree is the same idea, applied to a whole tree instead of one list: build it, check it, then lock it.

What the records add, compared with normal classes

Which way to go

  • You don't need Leaf and Branch types

    Use NodeQuadtree for everything and skip the freezer, the records and the interface. That's half the code.

  • You only want "no more inserts after node generation"

    Add a boolean locked to NodeQuadtree plus a lock() method, and make insert throw once it's locked. That's three lines instead of a second set of types.

  • You want the types, the safety and the polymorphism

    Freeze, as in Q17. Records if you like them short, final classes with arrays if you want them a little faster.

Q16 · Speed and the parent type

In a 10,000-node city, is the frozen tree faster or slower? And should QuadSquare be an interface or an abstract class?

Short answer

With the records from Q15, a search is a little slower than with NodeQuadtree: about 10 to 15% at 10,000 nodes. That comes from the lists inside the records, not from the interface. The same design with arrays is as fast as NodeQuadtree or a bit faster. Either way, a search takes about 0.3 µs at that size, so speed won't decide this. An interface and an abstract class measured the same, so choose by design. I'd pick the interface: it lets Leaf and Branch be records, and it describes what a square can do. An abstract class pays off when the kinds share real state or internal code. And since nodes will be your anchors for districts and distances, the frozen tree will be read by many steps, which is exactly when Q15 starts to pay off.

Measured on a 10,000-node city

I generated a bigger city with your algorithm: 36 starters (6 × 6, 1500 apart) on a 9000 × 9000 map, which gives 11,106 nodes. Then 200,000 searches near real nodes, run 9 times per version in rotating order, taking the middle time.

Run 1: interface and abstract class are equal

Both frozen versions use the same lists and differ only in the parent type. They stay within 1 to 2% of each other, which is run-to-run noise. Java handles a call through an interface and through an abstract class equally well here.

Run 2: the lists cost the speed

Swap the lists for arrays and the same interface design matches or beats NodeQuadtree. List.copyOf and toList() give read-only lists, and looping over them goes through an iterator object, while an array is walked with a plain index.

What 0.3 µs means in practice

Your seed-67 run makes about 9 isFarEnough calls per node. At 11,106 nodes that's roughly 100,000 searches, so about 30 ms for the whole city. The gap between these versions is a few milliseconds per city.

If you want the fast version

Use final classes with private arrays, not records. A record with an array in it hands that array out through its accessor, where it can be changed, and its equals compares arrays by identity instead of contents. The freeze step becomes nodes().toArray(new Node[0]) and children().stream().map(…).toArray(QuadSquare[]::new).

A rule of thumb that works well: an interface says what something can do, and an abstract class shares what something is made of. A frozen square mostly does things (find nodes, count, tell whether it touches a circle), and the shared state is only three numbers, so the interface fits. Effective Java, the standard book for this kind of question, says the same in its item "prefer interfaces to abstract classes".

An abstract parent becomes the better choice if squares grow more shared state that you don't want to repeat in every type, like a pointer to the parent square, the depth, or a cached node count, or if they need internal helper methods that shouldn't be public.

Since nodes will be your anchors

  • Many readers make the frozen tree worth it

    If districts, distance measurements and other steps all look up nodes, the tree is built once and read many times. That's the situation Q15 said to wait for.

  • Freeze again after any step that adds nodes

    If district corners or the new intersections from subdividing lots become nodes too, the frozen tree won't see them. Insert them into NodeQuadtree and freeze again, which takes about 0.12 ms at 11,000 nodes.

  • "Nearest node" is a different search

    Anchors often need "which node is closest to this point?" rather than "everything within 40". A quadtree can answer that too, by visiting the closest squares first and shrinking the radius each time it finds a closer node. That's worth its own question when you get there.

Q15 · Build, then freeze

What if the tree is built first, and a factory then turns it into Leaf and Branch classes behind one interface?

Short answer

That works, and it fixes both problems from Q14. The splitting happens in the mutable NodeQuadtree, so nothing ever has to change class. Afterwards, a factory walks the finished tree once and builds a copy out of Leaf and Branch objects, and for every square it has a real choice to make: leaf or branch. These are two well-known patterns. Building with a changeable object and then freezing it into an unchangeable one is the Builder idea, like StringBuilder → String. Leaf and Branch behind one interface, where a branch answers by asking its children, is the Composite pattern. The cost is that you have two versions of the tree, and the frozen one can't change, so it only fits once the nodes are final. In your generator that's right after node generation, which is when growStreet and isCrossingFree run.

Where NodeQuadtree comes from

Polymorphism and the switch, both

Polymorphism for shared questions

root.findWithin(…) and root.nodeCount() just work. A Branch passes the call to its children, and a Leaf answers itself. Java picks the right version, so the caller never checks what kind of square it has.

A switch when you need the kind

Drawing leaves one way and branches another is a switch (square) { case Leaf leaf -> …; case Branch branch -> …; }. Because the interface is sealed, that switch needs no default, and the compiler complains if a case is missing.

Factory class or factory method?

The separate QuadtreeFreezer class earns its place because it collects the leaves while it walks. That's state. Without the leaf list, a freeze() method on NodeQuadtree would be enough.

What it costs

  • Two versions of the tree

    Every change to NodeQuadtree, like a new field, means checking the factory and the records too. It's the same kind of "keep two things in step" work as GraphGeneratorCopy needed.

  • A snapshot doesn't follow changes

    If nodes are added after freezing, for example from a later step or a second batch of starters, the frozen tree doesn't see them. You'd insert them into NodeQuadtree and freeze again.

  • Memory and time are no issue

    Freezing your 161 squares makes 161 small objects once. Rebuilding the whole tree takes 0.03 ms (Q12), so freezing is in the same tiny range.

Is it worth it?

As something to learn from, yes: it puts two classic patterns, Builder-then-freeze and Composite, in about 70 lines, and each class stays small and free of nulls. For the generator, it pays off once several later steps read the tree: streets, lots, zoning and drawing. Today only growStreet would use it, so one class is still enough for now. Your idea isn't wrong, it's just early.

Q14 · Leaf and Branch types

Should Leaf be a class that extends Square, made by a Factory?

Short answer

Giving the two kinds of square their own types can be nice, but not as a subclass with a Factory. The catch is that a square starts as a leaf and turns into a split square later, and a Java object can't change its class. So every split has to throw the leaf away and put a new object in its place, in its parent or as the tree's root. A Factory adds nothing, because new squares are always empty leaves: there's no choice for it to make. If you want two types, the modern Java way is a sealed interface with two records, where insert hands back the replacement. If you just want to loop over the leaves more easily, a leaves() method does that with no new types. Why a Factory doesn't help here

Q13 · How the search really works

Why store a square's position at all, and how does the search avoid testing every square?

Short answer

You're right on the first point. A square's x, y and size follow from the map size and the path down to it, so storing them is optional: it's a saved copy of something you can work out. NodeQuadtree keeps that copy so each square can be used on its own, and the Q12 version passes it down instead. On the second point, the search does not test every square. It starts at the top, and when a square misses the circle, it stops right there: none of the squares inside it are ever tested. Your idea, testing every leaf, would test the 63 leaves that existed at an average isFarEnough call. Walking down the tree tests 19 squares instead. In the 9× city it's 405 against 24, because the walk grows with the depth of the tree, not with the number of squares.

Q12 · Storing a quadtree

How would you store a quadtree? Just the top-left and bottom-right of every square?

Short answer

Not as a list of corners, for three reasons. First, what makes it a tree is the links between the squares: each square knows its four children. A flat list of corners can't skip anything, so a search would test every square, which is brute force again. Second, for the corners themselves, one corner and the size are enough, because every square is exactly square and exactly half its parent. You can even work them out while walking down and store only the map size. Third, don't save the tree at all. It's built from the node positions, and rebuilding it for your 326 nodes takes about 0.03 ms. Save the nodes and streets, and rebuild the tree after loading, the way a database rebuilds an index.

The speed in Q11 comes from the nesting. A flat list of corners doesn't know that 110, 111, 112 and 113 sit inside 11, so skipping 11 can't skip them too. Each square has to be tested on its own. Memory isn't the problem

Your seed-67 tree has 161 squares: 121 leaves and 40 split squares. Even four doubles for every one of them is about 5 KB. Corners are worth avoiding because they add nothing to the search and because stored values can go out of date, not because of their size.

One corner and the size are enough

Q9 · City codes

What does CityConfig.parse do?

Short answer

It lets one text box accept two kinds of input. If the text is a whole number like 67, you get your default settings with that number as the seed. Anything else is treated as a full city code and goes through decode, which rebuilds every setting from the code. It's the "type a seed or paste a code" entry point.

Line by line

  1. input.strip() removes whitespace at both ends, so a pasted " 67\n" still works. It's the Unicode-aware version of trim().

  2. matches("-?\\d+") asks whether the whole string fits the pattern: -? is an optional minus, \d+ is one or more digits 0–9. The double backslash is only Java string escaping; the regex itself is -?\d+.

  3. If it fits, Long.parseLong turns the text into a long, and withSeed copies defaults with only the seed swapped. Width, starters, weights and the rest all stay the same.

  4. If it doesn't fit, the text goes to decode. That either returns the exact config stored in the code or throws an IllegalArgumentException with a readable reason: bad characters, too short, damaged, or the wrong version.

Q8 · Spatial indexes

What is a quadtree, and how would it help with the x/y positions?

Short answer

A quadtree is an index for positions. It covers the map with one square, and whenever a square holds more than a few nodes, it splits into four smaller squares. Busy areas end up with many small squares and empty areas with a few big ones. To find the nodes near a point, you only open the squares that touch the search circle and skip the rest of the map. Right now isFarEnough and growStreet check every node, and isCrossingFree every street, each time they ask what's nearby. With a quadtree, the first two do about a tenth of that work in your seed-67 city, and about a seventieth in a city nine times bigger. Node doesn't change at all: the tree sits next to the graph, like an index next to a database table.

How a search works

  1. Start with the square that covers the whole map, 1500 × 1500 for you.

  2. If the square doesn't touch the search circle, skip it. One comparison rules out the square and everything inside it.

  3. If it touches the circle and has been split, do the same for its four smaller squares.

  4. If it's a leaf, check its nodes one by one, exactly like isFarEnough does now. A leaf never holds more than 8.

The quadtree in Java

It only needs getX() and getY(), so it works with your Node class as it is. It needs java.util.ArrayList and java.util.List, and Math.clamp from Java 21 or newer.

Using it in GraphGenerator

Three loops change. Each one stops looping over the whole graph and loops over what the tree returns instead.

isFarEnough: same method, fewer nodes

isFarEnough already takes a Collection<Node>, so the method itself doesn't change. Give it the nearby nodes instead of graph.vertexSet(). Create the tree in run() next to the graph, and insert every node right after graph.addVertex, the starters included.

growStreet: only nodes within reach

Ask for the nodes within EDGE_SEARCH_RADIUS once per step. isWithinSearchRadius can go, because findWithin already checked the distance with the same <=.

isCrossingFree: only streets that could cross

The tree stores nodes, not streets, but it still helps here. Every street comes from growStreet, so none is longer than 120. If a street c→d crosses a→b, the crossing point is at most 120 from c and at most 120 from a, so c is within 240 of a. Testing the streets of the nodes within 240 therefore finds every possible crossing. A street can get tested twice, once from each end, which is harmless.

These examples pass index along as a parameter, the same way graph is passed. A field set in run() works too.

Benefits beyond speed

Node stays as it is

x and y stay plain doubles, and the graph doesn't change. JGraphT answers "what is connected to what", and the quadtree answers "what is near this point".

Same city as before

The tree returns nodes in a different order than vertexSet(). That could only matter on an exact score tie in growStreet, where the first candidate wins. It didn't happen in either test, and even then the same seed would still always give the same city.

Ready for the next steps

Fits clustered cities

Dense clusters split into small squares and empty countryside stays one big square, so the work follows where the nodes are. Starters with gaps between them are exactly that case.

Other options

  • A uniform grid

    Fixed cells, for example 120 × 120, each holding a list of its nodes. It's simpler than a quadtree, and just as fast when the search radii are fixed and the nodes are spread fairly evenly.   • JTS

    org.locationtech.jts.index.quadtree.Quadtree and STRtree, if you'd rather not write your own. JTS is already on your list for the concave hull. Its query returns everything whose box overlaps the search box, so you still do the exact distance check yourself.

Q7 · Performance

How much would the API connection cost, compared to learning GDScript or Rust?

Short answer

Very little, as long as the game calls the server once per turn and never once per frame. On the same PC a request takes about a millisecond, loading a whole city takes tens of milliseconds once, and starting Spring Boot takes a few seconds. Moving the generator to GDScript would cost more speed than the connection does, because GDScript runs much slower than Java. Rust would run faster, but Java is already fast enough, so that's months of learning for a speed-up you don't need. You'll also write some GDScript either way, because the Godot client itself is written in it.

Keeping the connection cheap

Send the city once

Nothing every frame

A full engine with an editor. MIT license, no fees.

Q5 · Entities and values

Why can't Starter just be a Node?

Short answer

It could, but a Node is the wrong kind of object for a config. A Node is one specific intersection in one generated graph: it has an identity, a database id and setters. A Starter is only a description, three numbers that say where growth starts and how much. A config needs descriptions, because it gets compared, encoded and reused for every run.

Two kinds of object

Java doesn't force this split, but it has names. Node is an entity: which object it is matters. Starter is a value object: only the data matters. Records are Java's tool for value objects.

Same decision as before

You deliberately didn't make Node a record, so JGraphT compares vertices by identity and two nodes at the same spot can never merge by accident. That's the right choice for the graph, and it's exactly what makes Node a poor fit for the config.

What would break with List<Node> in the config

Equal configs stop being equal

A record's equals compares each component, and for the list it asks every element. Node has no equals(), so it falls back to "is this the same object?". Two decodes of the same code would never be equal, and the round-trip test would fail on identical data.

The config can change after it was checked

The compact constructor checks the starters once. List.copyOf makes the list unmodifiable, but not the objects inside it, so a Node's setters still work afterwards. You'd get a code that decode() refuses to load. Starter has no setters, so a value that passed the check stays valid.

Every run would share the same nodes

run() puts each starter straight into the graph with graph.addVertex(seed). With Node in the config, every run would add the very same object. Once cities are saved, the first save gives that node a database Id, and saving the second city would then fail or update the first city's row instead of inserting its own.

How the two connect

The config keeps one Starter that never changes. Each run asks for its own fresh Node objects, so the graph and the database only ever see objects that belong to that run.

Q4 · Records

Starter is needed to make a config, so why is it a record inside CityConfig?

Revised 13 October 2026. The first answer explained how nesting works, not why Starter is nested. The new parts come first; the original explanation follows as background.

Short answer

Nesting only changes the name, not when or how you can use the type. Starter is a public, static member of CityConfig, so any class can create CityConfig.Starter objects before a config exists and pass them in. I nested it because a starter only means something as part of a city config, and its 5 bytes belong to the code format that CityConfig owns. A separate Starter.java would work exactly the same. It's a style choice, not a requirement.

Being an input doesn't rule out nesting

The Java library does the same thing with Map.Entry. The entries are created first and then passed in to build the map, exactly like starters and a config.

Why it's nested, and when to move it out

Reasons to keep it nested

  • A starter only means something as part of a city config. CityConfig.Starter says that in the name.
  • Its 5 bytes are part of the city code. Changing its fields means changing encode() and decode(), which sit in the same file.
  • It can't fully validate itself anyway: x and y are checked against the config's width and height.
  • It keeps a generic name like Starter out of the package.

Reasons to give it its own file

  • A lot of code builds starters directly, like the defaults in GraphGenerator or a future screen where you place them, and writing CityConfig.Starter everywhere gets clunky.
  • Starters get used without a config, for example to save or preview starter positions.
  • It grows its own logic and stops being a five-line record.

If you'd rather move it

Cut the record out of CityConfig and paste it into Starter.java in the same package. Outside CityConfig, CityConfig.Starter becomes plain Starter. Inside CityConfig nothing changes, because both types are in the same package.

What one record line writes for you

A record is a class whose header lists its data, and Java writes the boilerplate. Each component in the header becomes a field, a constructor parameter and an accessor method. The colours below show where each one ends up.

The generated toString() prints every component, which is what you saw in the test output: Starter[x=750.0, y=750.0, splitNumber=5.5].

What that means in practice

Immutable

The fields are final and there are no setters. To change something you build a new record. That's why withSeed() returns a new config.

config.withSeed(99);  // new object, config unchanged

Accessors use the plain name

You write config.width() and starter.x(), without get. Your Node class uses getX() because it's a normal class.

equals compares values

Two records holding the same data are equal, even when they're separate objects. The round-trip test relies on this.

CityConfig.decode(code).equals(defaults)  // true

Methods are allowed

toNode(), encode(), decode() and withSeed() are ordinary methods. A record can have as many as you like.

Static fields yes, instance fields no

static final int VERSION = 1; compiles. Adding private int counter; to the body doesn't: all instance data has to go in the header.

No subclasses

A record is final and can't extend another class, because it already extends java.lang.Record. It can implement interfaces.

The compact constructor

This is the part of CityConfig that looks the most unusual. It has no parameter list, because the parameters are already listed in the header.

When you call new CityConfig(…), this happens in order:

  1. The arguments arrive as parameters named after the components: width, starters, seed and so on.

  2. Your code runs. Here, width still means the parameter, because the fields aren't set yet. Every checkRange runs, and starters is replaced with an immutable copy.

  3. Java copies each parameter into its field at the closing brace. this.starters gets the copy, not the list that was passed in.

  4. The object exists, with values that passed every check.

If a check fails

checkRange throws in step 2, so steps 3 and 4 never happen. An invalid CityConfig can't exist, which means encode() never has to deal with a value it can't store.

Why List.copyOf

If someone passed in an ArrayList and added to it later, the config would change behind your back. List.copyOf makes an unmodifiable copy and also rejects null entries.

You can't set the fields yourself

Writing this.width = width; inside a compact constructor is a compile error. Java does that part for you, at the end.

The long form also works

A normal constructor with all 12 parameters spelled out and 12 this.x = x lines is allowed too. The compact form is the same thing without the repetition.

Rules that keep codes reliable

  • Generate from the decoded config

    Rounding to tenths loses precision: a weight of 1.23 is stored as 12 and comes back as 1.2. normalized() runs decode(encode()), so the city you generate is always the one the code reproduces.

  • Bump VERSION when the generator changes

    The same code fed to a changed algorithm gives a different city. With a new version number, old codes fail with a clear message instead of quietly producing something else.

  • Mask signed bytes

    Java bytes run from −128 to 127. A stored 200 comes back negative unless you mask it:

    stored byte0xC8
    →
    buffer.get()-56
    →
    buffer.get() & 0xFF200

  • Field order is the format

    encode and decode must write and read the fields in exactly the same order. The round-trip test catches a mistake here right away.

  • Starter nodes are settings too

    A count byte comes first, then 5 bytes per starter. With your three commented-out starters added, the code grows to 55 characters.

Q2 · Seeding

How do we get consistent seeds?

Short answer

new Random() picks a different seed every run. new Random(seed) gives the same sequence of numbers every time for the same seed. Every random call in GraphGenerator already goes through one Random, so seeding it is the whole fix, as long as the numbers get used in the same order each run.

The random numbers are one long tape

A seeded Random hands out numbers in a fixed order. Each stage of the generator takes the next numbers off the tape. The city only repeats if every stage takes the same numbers in the same order.

  • node generation
  • edge shuffle
  • one extra draw

Dashed cells now get a different number than before. Number 9 used to be the first shuffle number; now node generation takes it. Same seed, different city. That's expected whenever the code or the settings change. Illustration only: the real tape has 16 angle/distance pairs per splitting node, plus split rolls.

Rules for staying deterministic

  • Only use that one Random

    Math.random(), ThreadLocalRandom and anything based on the clock bypass the seed.

  • Keep the iteration order stable

    JGraphT's vertexSet() and edgeSet() keep insertion order, so you're fine today. A plain HashSet<Node> isn't: Node has no hashCode(), so it uses the identity hash, which changes every run. Use LinkedHashSet or LinkedHashMap. This matters most in growStreet, where a tied score goes to whichever candidate comes first.

  • No parallel use

    Threads pulling from the same Random get their numbers in an unpredictable order.

  • StrictMath if seeds are shared between machines

    On one machine, Math.sin, cos and atan2 always give the same results. Across JVMs or CPUs they can differ in the last bit, which is enough to flip an isFarEnough check. StrictMath gives identical results everywhere.

Separate tapes per stage, for later

Each stage then draws from its own tape, so how many numbers one stage uses can't shift another stage's numbers. With only two stages, where the edges depend on the nodes anyway, this changes little. It starts to matter once you add more stages, especially when you insert one between existing stages.
