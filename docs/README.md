| Q23 | 2026-10-23 | Why does `Leaf.collectWithin` do its own math per node instead of using `touches`? | [touches-vs-node](java-notes.html#touches-vs-node) | Different questions: `touches` = can the circle reach a square (clamp to its closest point first); the loop = is this one point inside. Both end with `dx² + dy² ≤ r²`, so a shared `static within(px, py, x, y, radius)` in `QuadSquare` works (tested, identical results). Static interface methods aren't inherited: `Leaf` must call `QuadSquare.within(…)` (unqualified = compile error); `default` methods like `touches` are. Leaf still calls `touches` first to skip a whole leaf. |
| Q22 | 2026-10-20 | Why does `findWithin` return `void` and fill a list? Are x and y relative to the square or the whole map? | [find-within](java-notes.html#find-within) | Callers should get a list: final code now has `List<Node> findWithin(x, y, radius)` on top of a recursive `void collectWithin(x, y, radius, result)`. Every level returning its own list measured 2.4× slower; the wrapper costs 3–10% vs a reused list (11k nodes). x and y are map coordinates (the circle's centre, like `node.getX()`), the same for every square; each square compares them with its own map-coordinate `minX/minY/size` via clamp. |
| Q21 | 2026-10-19 | The conclusive quadtree code, with every class we agreed on | [final-code](java-notes.html#final-code) | Full code for `QuadTreeBuilder`, `QuadTree`, `QuadSquare`, `Leaf`, `Branch` (package `generation.quadtree`) plus the changed `GraphGenerator` lines. Updated 2026-10-20: `findWithin` returns a list, `collectWithin` does the recursion. Tested: compiles with the real `Node.java` under `-Xlint:all`; matches brute force on 3,000 searches; frozen = builder order; and seed 67 wired to the tree gives the identical 326 nodes / 549 streets. |
| Q20 | 2026-10-19 | Won't a big quadtree use a lot of memory if it isn't stored in a database? | [tree-memory](java-notes.html#tree-memory) | No: it points at the existing nodes and has 1 square per 2–3 nodes (~90 bytes each). Measured frozen tree: 0.28 MB at 11k nodes, 3.4 MB at 100k, 40 MB at 1M, less than the nodes and ~1/15 of the JGraphT graph (52 MB at 100k). The builder is garbage collected after `build()`. Asking MySQL per search would be ~1000× slower; save nodes/streets, rebuild the tree after loading. MySQL `SPATIAL INDEX` (R-tree) only for later API queries. |
| Q19 | 2026-10-19 | Since every tree ends up frozen, shouldn't the frozen one just be called `QuadTree`? | [naming](java-notes.html#naming) | Yes. Five types: `QuadTreeBuilder` (changeable class: `insert`, `findWithin`, `build()`, private `freeze`), `QuadTree` (record: `root`, `leaves`, `findWithin`), `QuadSquare` (sealed interface: `findWithin`, `nodeCount`, default `touches`), `Leaf` and `Branch` (records). Like `StringBuilder` → `String`. Avoid `Frozen` (adjective) and `QuadNode` (`Node` already means intersection). |
| Q18 | 2026-10-18 | Why would you need to freeze the tree into records? | [why-freeze](java-notes.html#why-freeze) | You don't: freezing exists only to get `Leaf`/`Branch` types (they can't be built directly, Q14). It buys an unchangeable tree, typed no-null squares with polymorphism, and a precomputed leaf list; the same idea as `CityConfig`'s `List.copyOf(starters)`. Records are just short immutable classes. Options: `NodeQuadtree` only; a `lock()` flag that makes `insert` throw; or freeze (Q17). |
| Q17 | 2026-10-18 | What do I need to write for the interface-based quadtree? | [build-sheet](java-notes.html#build-sheet) | Build sheet, signatures only (Max writes the bodies). Package `generation/quadtree`: class `NodeQuadtree` (+ read-only getters), `sealed interface QuadSquare permits Leaf, Branch` (`findWithin`, `nodeCount`, default `touches`), records `Leaf`, `Branch`, `FrozenQuadtree` (`of`, `findWithin`), factory class `QuadtreeFreezer` (`freeze`, `leaves`). Five `GraphGenerator` changes. Done when seed 67 still gives 326 nodes / 549 edges. |
| Q16 | 2026-10-18 | In a 10,000-node city, is the frozen tree faster or slower? Interface or abstract class? | [interface-or-abstract](java-notes.html#interface-or-abstract) | Measured on 11,106 nodes (36 starters, 9000²): frozen records ~10–15% slower per search than `NodeQuadtree` because of their lists; the same design with arrays matches or beats it. ~0.3 µs per search, ~30 ms per city, so speed doesn't decide. Interface vs abstract class: equal speed. Pick the interface (records allowed, "what it can do"; *Effective Java* "prefer interfaces"); an abstract class only for real shared state/internals. Nodes as anchors make freezing worth it; re-freeze after steps that add nodes (0.12 ms). |
| Q15 | 2026-10-18 | What if the tree is built first, and a factory then turns it into Leaf and Branch classes behind one interface? | [freeze](java-notes.html#freeze) | Works, and fixes Q14's problems: split in the mutable `NodeQuadtree`, then `QuadtreeFreezer` makes a `Leaf` or `Branch` per square (a real choice), behind `sealed interface QuadSquare` (Composite pattern; Builder-then-freeze like `StringBuilder` → `String`). Fits after node generation: `growStreet`/`isCrossingFree` and later steps read the frozen tree; `FrozenQuadtree` also keeps a leaf list. Tested: same nodes, same order. Costs: two versions to keep in step, snapshot must be re-frozen if nodes change. Worth it once several steps read the tree. |
| Q14 | 2026-10-18 | Should `Leaf` be a class that extends `Square`, made by a Factory? | [leaf-classes](java-notes.html#leaf-classes) | Not as a subclass + Factory: a leaf turns into a split square, and a Java object can't change its class, so every split must replace the object in its parent/root (same lesson as the old Building/owner question). A Factory would only ever make empty leaves. If you want two types: `sealed interface Square permits Leaf, Branch` with records, `insert` returning the replacement (tested). For easy looping: a `leaves()` method. Recommendation: keep `NodeQuadtree` as one class. |
| Q13 | 2026-10-18 | Why store a square's x, y and size if they follow from the map size? And how does the search avoid testing every square? | [quadtree-walk](java-notes.html#quadtree-walk) | Storing the position is optional: it's derived from the map size + path, and `NodeQuadtree` keeps it only so each square works on its own (passing it down, as in Q12, is equally valid). Stored copies can go stale: `Node.degree` is never set, while the generator uses `graph.degreeOf`. The search walks down and stops at misses, so squares inside a skipped square are never tested. Average per `isFarEnough` call: 19.3 tests vs 63 leaves today, 24.2 vs 405 in the 9× city. Worst spot (750, 750): 53 of 161. Interactive demo + per-level table. |
| Q12 | 2026-10-18 | How would you store a quadtree? Just the top-left and bottom-right of every square? | [quadtree-storage](java-notes.html#quadtree-storage) | Not as corners: the parent/child links make it a tree, and a flat corner list must test every square (161 for seed 67). One corner + size is enough, or none (pass position down while walking). Don't persist it: rebuild from node positions (0.03 ms for 326 nodes, 7 ms for 100k). To write it down, use path codes like `"112"` (= Morton/Z-order), decoded by `squareOf`. |
| Q11 | 2026-10-15 | How does a quadtree actually work, step by step? | [quadtree-steps](java-notes.html#quadtree-steps) | Two steppers. Part 1: 10 points, capacity 2, 30 steps through inserts, 4 splits and one radius search (map + tree diagram), plus a table linking each step to its line in `NodeQuadtree`. Part 2: replays all 3,072 `isFarEnough` calls for seed 67 (2,747 rejected, 325 accepted), each with your loop's count vs the quadtree's; totals end at 317,305 vs 29,261, matching Q8. Your loop wins 243 single calls (early exit), but loses overall. |
| Q10 | 2026-10-14 | How did you make the visualizer for Q8? | [demo](java-notes.html#demo) | Plain HTML/CSS + ~120 lines of JS, no libraries. A BigInt copy of `java.util.Random` rebuilds the real seed-67 nodes (326, same as Java), `class Square` mirrors `NodeQuadtree`, and `render()` redraws an SVG with `viewBox="0 0 1500 1500"` (map units, like `drawGraph`'s 1500² image) after every click. Includes a Swing `QuadtreeView` sketch and the Spring Boot headless gotcha. |
| Q9 | 2026-10-14 | What does `CityConfig.parse` do? | [parse](java-notes.html#parse) | One input for both: a whole number (`-?\d+`) means default settings with that seed (`withSeed`), anything else goes to `decode` as a city code. Never ambiguous, because codes start with `A` until version 208+. Watch-outs: a number too big for a `long` throws Java's own `NumberFormatException` message, and the seed path doesn't normalize `defaults`. Not called anywhere yet. |
| Q8 | 2026-10-13 | What is a quadtree, and how would it help with the x/y positions? | [quadtree](java-notes.html#quadtree) | An index that splits the map into squares (split into four when a square holds more than 8 nodes), so "what's near (x, y)?" only opens nearby squares. Measured on a copy of the generator: ~10× fewer checks in `isFarEnough`/`growStreet` today (326 nodes), ~70× in a 9× bigger city (1.9 s → 0.2 s), same streets. `isCrossingFree` uses it too: a crossing street has an end within 240 of `a`. Includes a full `NodeQuadtree` class and an interactive demo on the real seed-67 nodes. |
| Q7 | 2026-10-13 | How much would the API connection cost, compared to learning GDScript or Rust? | [api-cost](java-notes.html#api-cost) | Very little if it's called per turn, not per frame: ~1 ms per request, tens of ms to load a city once, a few seconds of Spring Boot startup. GDScript would make the generator slower than the connection costs; Rust is months of learning for speed Java already has. C# is the one-program option if ever needed. |
| Q6 | 2026-10-13 | Godot or libGDX for the 3D city, or something better? | [engine](java-notes.html#engine) | First decide where the Java code runs. Godot as a client with Java/Spring as the simulation server gives the best 3D, editor and UI. To stay 100% Java: jMonkeyEngine for 3D, libGDX if 2D/top-down is enough. Lots and zoning don't depend on the choice. |
| Q5 | 2026-10-13 | Why can't `Starter` just be a `Node`? | [node-vs-starter](java-notes.html#node-vs-starter) | `Node` is an entity (identity, setters, database `Id`); `Starter` is a value object. With `List<Node>`, configs wouldn't compare equal, could change after validation, and every run would share the same graph nodes. `starterNodes()` makes fresh Nodes per run. |
| Q4 | 2026-10-12, revised 10-13 | `Starter` is needed to make a config, so why is it a record inside `CityConfig`? | [records](java-notes.html#records) | Nesting only changes the name: a public nested record is static, so anyone can create `CityConfig.Starter` objects first and pass them in (like `Map.entry` → `Map.ofEntries`). Only a *local* or *private* record couldn't be an input. Nested because a starter is part of the city-code format; a separate `Starter.java` would work the same. Also covers what a record generates and the compact constructor. |
| Q3 | 2026-10-12 | How do the settings and the seed become one shareable code? | [city-codes](java-notes.html#city-codes) | An encoding, not a hash: version + every setting + seed + checksum packed into 31 bytes, written as 42 URL-safe Base64 characters. |
| Q2 | 2026-10-12 | How do we get consistent seeds? | [seeds](java-notes.html#seeds) | Seed the one shared `Random`. Keep the draw order fixed: one RNG, stable iteration order, no threads, `StrictMath` if seeds are shared between machines. |
| Q1 | 2026-10-12 | What does `continue` do in `growStreet`? | [continue](java-notes.html#continue) | Skips the rest of the current iteration of the innermost loop (the `for` over candidates). Used as guard clauses. |
