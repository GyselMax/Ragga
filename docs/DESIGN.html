Overview

The project

What Ragga is

A multiplayer city simulation that runs on its own before players arrive

Ragga generates a city as a street graph, fills it with households and companies, and runs it week by week on a Java server. Cities: Skylines II is the design reference. The core rule, carried over from the old design: the city must sustain itself. Economy, jobs, spending and housing keep working with no player input. Players join a living world; they aren't the reason it exists.

Built so far

  • Graph generation: intersections and streets from a seed
  • City codes: settings + seed in 42 characters
  • Quadtree types (builder still in progress)

Still to build

  • The economy loop, lots and zoning
  • People, jobs and the tick loop on the server
  • Life events and the multiplayer client

Design

How it works

Generation

From starter nodes to a street graph

The city is a JGraphT graph: nodes are intersections, edges are streets. Node growth and street growth come from the worldsmith road-network write-up (zero.re); Parish & Müller (2001) is background reading.

1 · Starters

Seed nodes with a position and a split number.

→

2 · Node growth

Breadth-first: each node tries 16 candidates 40–120 away and keeps those far enough from everything.

→

3 · Streets

growStreet extends streets node by node, picking the best candidate that passes every rule.

→

4 · Quadtree

Spatial index so “what's near here?” stops scanning every node.

→

5 · Lots + zoning

Blocks from the graph's faces, sized by the economy spike.

Street rules (all must pass)

  • Both ends have fewer than 4 streets
  • The two nodes aren't already linked
  • It doesn't close a triangle
  • No angle under 30° with an existing street at either end
  • It crosses no existing street

Choosing the next node

  • Only nodes within 120 are candidates
  • Score = 1 × straightness + 4 × closeness
  • The street ends when no candidate passes
  • Start nodes are shuffled by the seeded random

All of these travel in a city code (CityConfig): a version byte, every setting, the starters, the seed and a checksum, packed into URL-safe text. One starter makes a 42-character code. The quadtree is kept in memory and rebuilt after loading; it's never saved.

Determinism rules

Same code in, same city out, on every machine

City codes, golden tests and crash recovery on the server all depend on this. Break one rule and the city quietly changes between runs.

  1. One shared seeded Random, drawn from in a fixed order.
  2. Ordered collections only. Use lists, ArrayDeque and JGraphT's insertion-ordered sets. Never iterate a HashSet or HashMap keyed on Node: nodes hash by identity, so the order changes every run.
  3. Single-threaded generation and ticks.
  4. StrictMath for sin, cos and atan2 (decided 2026-10-26), so results don't depend on the CPU or JVM.
  5. Player commands apply only at tick boundaries, in queue order, so a replay gives the same result.
  6. A change that alters the output for the same code bumps CityConfig.VERSION and re-pins the golden test in the same commit.

Multiplayer server

The server holds the city in memory and has the final say

Ragga is multiplayer. The server is the single authority: players send commands, the server checks them and applies them at the next tick, and everyone receives the result. Agreement comes from the server process, not from database writes, so there is no database write per tick.

Crash recovery

Load the latest snapshot, then replay the logged commands. This gives back exactly the same city only because the simulation is deterministic (see the rules above).

Economy spike

Close the money loop before building the map for it

The old roadmap tested stability (step 7) before income, shops, companies and life events existed, and its money had nowhere to go: tax had no receiver and industry had no buyer. The spike fixes that first. It's plain Java with no map, no Spring and no database, and it tells generation what to produce (jobs and homes per lot).

Starting point for the weekly order (from design-2.0)

Salary → tax → debt → rent → shops → savings. Adjust it for weekly ticks once the monthly-costs question is settled.

The spike passes when

  • Money balances every tick: the city's total changes only by export income minus imports.
  • Employment stays in a band over 1,000 ticks (about 19 years); the band is still to set.
  • The same seed gives the same result, run twice.
  • All of it in a plain JUnit test: no Spring, no database, no map.

Plan

Order of work

Roadmap

Seven steps; checks come after what they check

  1. Generation done

    Node growth and streets. Seed 67 → 326 nodes / 549 streets.

  2. Safety net and quadtree now

    • Secure the work: archive the old repo's uncommitted tree on a branch and push it; make the staged quadtree files match the working tree.
    • Safety net: generation in a plain class that takes a CityConfig; switch to StrictMath; a JUnit golden test (counts plus an order-independent street fingerprint) and a brute-force invariants check.
    • Quadtree: builder written by hand against a brute-force equivalence test, then wired into the three scans. Two evenings at most.

    Done when ./mvnw test passes with MySQL stopped, and the golden test is unchanged after the quadtree is wired in.

  3. Economy spike next

    Plain-Java money loop with treasury and outside market (see Economy spike).

    Done when 1,000 weekly ticks balance money, keep employment in its band, and repeat exactly.

  4. Lots and zoning

    Blocks from the graph's faces; zone mix sized by what the spike needs. Watch for streets passing close to unrelated intersections, which makes sliver blocks.

  5. People, jobs and the server tick loop

    Households and inhabitants on lots, job matching, and the real tick loop: server memory, command queue, clock, snapshots and command log.

  6. Minimal life events

    Hiring, layoffs, and deaths replaced by births. Nothing more until this is stable.

  7. Players

    The multiplayer client; player actions as commands (buy buildings, hire, take loans).

Deferred

Counter-offers on job changes, homelessness penalties, personal bankruptcy, the 3D engine choice, and portfolio extras (CI badge, JMH benchmarks, a generic quadtree library).

Working rules

How work on Ragga happens

  1. Max writes the code. AI sessions advise and explain, and write reference code only when asked.
  2. Any change in src/ starts with a written plan.
  3. Explanations and reports are HTML pages, not markdown.
  4. Before every commit: check git status and git diff --cached, and run ./mvnw test.
  5. The golden test stays green. A deliberate change re-pins it and bumps CityConfig.VERSION in the same commit.
  6. Keep this page current: update Current state and the roadmap chips when a step finishes.

Glossary

Words used in the code and this doc

Node
An intersection in the street graph.
Edge, street
A connection between two nodes.
Starter
A node the generator starts from: a position plus a split number. The code also calls these “seeds”, which is easy to confuse with the random seed.
Split number
How many more generations a node branches. The whole part always happens; the fraction is the chance of one more. 5.5 → 4.5 → … → 0.5, which branches half the time.
Random seed
The number that makes the random choices repeatable (67 in the golden test).
City code
Every setting, the starters and the random seed packed into one short shareable text.
Golden test
A test that locks one seed's output (326 / 549), so accidental changes show up.
Quadtree
A spatial index that splits the map into squares, so nearby nodes are found without checking all of them.
Tick
One simulation step: one week.
Treasury
The city's account: receives tax, pays public jobs and services.
Outside market
A buyer beyond the city that pays a set price for industry and farm output.
Snapshot
The whole city's state, saved every K ticks.
Command log
Every accepted player command since the last snapshot, used for crash recovery.
Spike
A small, throwaway-friendly prototype that answers one question: does the money loop hold?
